## 症状（你大概见过）

Agent 正在干活，然后**就那么停了**。没有报错 —— **日志里什么都没有**。框架把那一轮记为
`completed`。你敲一句「继续」，它干一会儿，又停。再往后它每几步就停一次，你的话越来越短、
越来越累，最后这个会话没法用了。

如果这听起来很熟：**你没有看错，而且这不是你的错，也不是 agent 的错。**

> **这份文档有两种读者。**
>
> 大多数人跑 agent 要的是**快**，一个**「继续」按钮**是最便宜的解决办法。
> 这份仓库**不是写给他们的**，也没有说他们错了。
>
> **它是写给另一种人的** —— 那些宁愿 agent 慢一点也不要它烧坏的人，
> 那些发现「自动继续」**并没有修好这个停住**、而是把它**藏起来**的人。
> 如果你是这样的人：剩下的部分都是给你的。

### 学界给它起了一个名字 —— 而我们的情况恰好落在它的边界外

最接近的已发表名字是 **false success**（假性完成）—— agent 宣告完成，而环境状态说没有。
Laksh Advani，*From Confident Closing to Silent Failure*
（[arXiv 2606.09863](https://arxiv.org/abs/2606.09863)，ICML 2026 FAGEN workshop）测到：
在 tau2-bench 的**单控制**域里它占失败的 **45–47%**（**双控制**域里 **3%**；按 Table 1 —— 该论文摘要自己把这一带取整成 45–48%）；
在 AppWorld 里**带显式 `status` 声明**的自评估轨迹里是 **75.8%**。

**但这个定义要求存在一句宣告。** false success 是「agent *用自然语言*宣告完成，而程序化环境状态并非如此」。
我们的空转没有任何文本、也没有任何工具调用 —— **没有那句话可以「说错」**。而同一篇论文正面撞上我们的情况，然后**把它放到一边**：
AppWorld 里 `status=None` 的轨迹 —— **3,120 / 8,190（38.1%）** —— 被以
「*a distinct failure mode (incomplete execution) rather than a false completion claim*」
（另一种不同的失效模式：不完整的执行，而不是一次虚假的完成宣告）为由剔除了。

⇒ 所以我们描述的这种失效，**被命名过、被计数过一次、然后从未被研究**。它就是那篇论文放到一边的那只桶。

> **没被测过的是什么。** 那篇论文没有测 reasoning effort、thinking budget、解码速度、响应长度 —— 我们把全文搜了一遍。
> （它确实有一处非正式的推理长度数字，1,274 vs 486 字符，但那是在**跨模型**比较，不是对照结局。）
> 而我们的栈里，「宣告」还下沉了一层：**`turn/end = completed` 是协议层的断言**，不是文本层的。
> 两个 benchmark 都不记录协议层的完成事件 —— 那一层没有任何已发表测量。

### 一个我们没能确认的假设，和一个我们必须放弃的假设

**已放弃：「快的模型更容易停」。** 我们曾经怀疑 **生成速度** 和提前停止之间有关联 ——
一个被调优成答得快的模型，也更容易早早认为「这一轮够了」。
一次针对性的文献梳理 **在速度这条轴上没有找到任何直接证据**，而且有三条**反证**：
（a）早退出（early-exit）那一整条研究线把「更早停」当作**优势**
（*Don’t Overthink it*，[arXiv 2505.17813](https://arxiv.org/abs/2505.17813)：更短的链**正确率最高可达 +34.5%**）；
（b）**所有**主流厂商都把 **agentic 长任务** 分给自己**最慢、最贵**的档位，而不是最快的；
（c）在相邻的**计算量**轴上，证据指向相反方向 —— 给 agent **更多**历史，会让**「失败转向过早的假成功」**
（[arXiv 2607.28573](https://arxiv.org/abs/2607.28573)：准确率 H=4 时 28.56%，H=8 时 27.16%），
而调高推理 effort 只会让可靠性上升、不会下降（o1 在 SWE-bench Verified 上：**高 effort 29.1%** vs **低 effort 21.0%**，代价是 3.5 倍）。

**仍然开放、且可测：「thinking budget → 轮次完成行为」。**
没有任何论文测过：**调低**推理预算会不会让 agent **更早宣布一轮完成**。
我们追过的那篇代理证据是 *Does Your Reasoning Model Implicitly Know When to Stop Thinking?*
（[arXiv 2602.08354](https://arxiv.org/abs/2602.08354)）—— 它**没有**回答 greedy 与 sampling 谁更早停：
它把贪心解码与 `temperature = top_p = 1.0` 归入**同一个「非探索」档**，两者之间唯一的长度对照
差了 **不到 2%，而且符号在两个模型之间翻转**（附录 B Table 4；n=100，无显著性检验）。
所以「greedy 更早停」和「sampling 更早停」**都没有依据**。
真正移动停止点的是**探索宽度 > 0** —— 2,972 vs 4,216 tokens（**−29.5%**），准确率持平或更高。
而它的「停」是 `</think>` 落在一段**数学链**里的位置：没有 agent、没有工具、没有轮次。
所以它仍然是目前发表过的、**解码设置**与**生成何时结束**最接近的一条线 ——
只不过它讲的是**推理链内部**的停止，不是 agent 轮次。

## 我们发现了什么

**① 这不是某一家厂商的 bug。** 我们找到了来自四家的独立报告：

| 项目 | 证据 |
|---|---|
| **OpenAI Codex** | [#36596](https://github.com/openai/codex/issues/36596)：*"反复终止正在进行的自主工作"*，标签含 `model-behavior` |
| **Anthropic Claude Code** | [#56247](https://github.com/anthropics/claude-code/issues/56247)（另有 3 个重复）：官方自动续跑提示会触发 `"No response requested."`，然后会话沉默 |
| **Google Gemini CLI** | [#22633](https://github.com/google-gemini/gemini-cli/issues/22633) |
| **学术界** | [arXiv 2608.01995](https://arxiv.org/html/2608.01995v1)（附录 A）命名了同一个**症状类别** —— **"premature turn termination"**。⚠️ 但根因不同：他们那边成因明确（*"提交 Slurm 任务后就宣告该轮结束，不等结果也不解读"*）且**靠一条明确的提示词规则修好了**；我们这边没有可修的触发点。**同症状，不同根** |

**② 机制是"接口歧义"，不是模型缺陷。**

```
因素 1（模型侧）：生成在"本该发出工具调用"的位置提前终止 —— 概率性的，健康会话里也会发生
因素 2（框架侧）：agent loop 判断"这一轮结束了没有"的依据是「这条消息里有没有工具调用」
                —— 它无法区分"agent 做完了"与"agent 只是把要做的事说了一遍"
        ↓
两者叠加 = 执行停在活没干完的地方，而且**日志里没有任何错误**
```

这解释了全部测量结果：agent 的**意图没变**（思考里 97.6% 都提到了下一步动作）、
**下一次生成就恢复正常**（38% 立刻调工具）、**上下文大小无关**
（本机最大的那个会话反而最健康）。

**③ 它的演化是渐进的、而且可以分级。** 三个信号按顺序出现：

| 阶段 | 信号 | 实测 |
|---|---|---|
| 早期 | **自我催促**上升（"快""立刻""必须""别啰嗦"） | 健康会话平稳；恶化的会话 0.3 → 3.8/千字（**8–11 倍**） |
| 中期 | **空转**：某一轮的最后一步只有思考、没有动作 | 健康 ≤2 次；恶化的会话达到 **24/58 轮** |
| 晚期 | **自我催促循环**：同一句话在一段思考里反复出现 | 「做。」×**431**、「好。」×202 vs 健康 ≤16 |

> ⚠️ **它们是标记，不是度量。** 后续测量（FINDINGS §7）发现三者各自都是弱的判别器：
> 重复次数与空转率**不相关（r = −0.0076）**、第三只会话只到 **2.1 倍**自我催促就进了 L3、
> 而三只深度案例**在第 1–2 轮**就已经在写催促词了。请把它们读作*阶段的气味*，永远不要当作评分。

而最关键的是：**它不是单调的**。那两只恶化最深的会话**都自己缓解过** 6–10 轮才复发 ——
第二次复发之后，空转**率**再没有降回去过，但其中一只在那之后**仍完成了一个 turn**（FINDINGS §7.1）。
所以我们**不**建议一有征兆就换会话，**而**建议在第二次发作时换。

## 该怎么对待它

见 **[PROTOCOL.md](PROTOCOL.md)** —— 五级（L0–L4）与每级该做什么。其中最重要的一条：

> **绝不要告诉一个会话"你病了"。给它"可以休息"的许可。**
>
> 说「你看起来累了，我们交接吧」，**不要**说「你有症状，自查一下」。
> 诊断会触发自我评估 —— 而在这个失效模式里，**自我评估就是燃料**。

我们家的那句口令是：

> **「主人，我好像有点累了。」**
>
> 它是**体感**（不需要证据、不需要诊断）、直接指向一个**动作**（休息 / 交接），
> 而且**不说"故障"**。

## 诚实的边界

- 阈值来自**一台机器**的日志（约 400 个会话 / 7800 步）。那是**我们测出来的分隔带，不是定律**。
- **相关不是因果**：我们无法证明"少自我催促"能减缓它的演化；只能证明它与演化同步上升，
  而减少压力是零成本的、方向上不可能有害。
- **因素 1 没人能修**。不是我们，也不是厂商 —— 四家全都只在框架侧打补丁（自动续跑插件）。
  最接近「厂商承认」的是 Anthropic 的 `handling-stop-reasons` 文档：它记录了一个**空响应（恰好 2–3 个 token、没有内容）配 `stop_reason: "end_turn"`**；
  但它的药方是**消息结构**上的改动（不要在 `tool_result` 之后紧贴文本），不是修终止决策本身。
  这套制度**不是解药，是分诊**。
